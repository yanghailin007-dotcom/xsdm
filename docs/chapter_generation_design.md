# 正文生成设计方案

## 背景
对话式设定生成完成后，需要进入**正文生成**阶段。核心要求：
1. **每卷在一个对话中生成**（上下文连贯）
2. **每批次 6 章**后做一次**对齐质检**（正文 vs 细纲/大纲/设定）
3. **输出格式便于上传**（.md，按章节拆分）

---

## 一、整体流程

```
设定+大纲+细纲已保存
    ↓
进入「正文生成」页面
    ↓
选择卷号 → 读取该卷细纲
    ↓
▶ 开始生成（每批次 6 章）
    ↓
AI 逐章输出正文（SSE 流式）
    ↓
批次完成 → 自动保存 6 个 .md 文件
    ↓
🔍 对齐质检（正文 vs 细纲）
    ↓
显示质检报告
    ↓
├─ 通过 → 继续生成下一批
└─ 不通过 → 显示修改建议 → 用户确认重写
    ↓
全部完成后 → 项目目录下有完整 chapters/
```

---

## 二、后端 API 设计

### 2.1 生成正文 `POST /api/conversation/generate-chapters`

**请求：**
```json
{
  "project_id": "神豪经验值",
  "volume_number": 1,
  "start_chapter": 1,
  "batch_size": 6,
  "model": "deepseek-v4-pro"
}
```

**后端逻辑：**
1. 读取项目目录下的 `settings.md` + `outline.md` + `detailed_outline_vol1.md`
2. 提取该卷第 1-6 章的细纲
3. 构建 prompt（见下文）
4. 调用 AI API，**SSE 流式返回**
5. 按 `### 第X章` 分隔，自动拆分为 6 个 `.md` 文件保存到 `chapters/`

**Prompt 结构：**
```
你是专业网文作家。请根据以下设定和细纲，生成第1章到第6章的正文。

【核心设定】
{settings}

【本卷大纲】
{volume_outline}

【章节细纲】
第1章：标题
- 场景：...
- 情绪：...
- 字数：3000
...

要求：
1. 每章3000-5000字
2. 严格按细纲中的场景、情绪曲线写作
3. 爽点要足，打脸要狠，期待感拉满
4. 主角不能圣母、不能降智
5. 每章结尾留钩子
6. 每章用 "### 第X章 标题" 作为分隔标记
7. 不要输出任何说明文字，直接输出正文
```

**SSE 流格式：**
```
data: {"content": "### 第1章 标题\n\n正文内容..."}
data: {"content": "第二章内容..."}
...
data: [DONE]
```

**保存文件：**
```
小说项目/{username}/{书名}/chapters/
├── 第1章_标题.md
├── 第2章_标题.md
├── ...
```

---

### 2.2 对齐质检 `POST /api/conversation/align-check`

**请求：**
```json
{
  "project_id": "神豪经验值",
  "volume_number": 1,
  "chapter_range": "1-6",
  "model": "deepseek-v4-pro"
}
```

**后端逻辑：**
1. 读取刚生成的 6 章正文
2. 读取对应的细纲
3. 构建对齐质检 prompt
4. 调用 AI，非流式，返回 JSON 报告

**Prompt 结构：**
```
你是资深网文编辑。请将以下生成的正文与原始细纲进行对比质检。

【原始细纲】
{detailed_outline_vol1 的 1-6 章}

【生成的正文】
{第1章正文}
{第2章正文}
...

请严格检查：
1. 正文是否严格遵循了细纲中的场景设计和情绪曲线？
2. 是否有偏离大纲的毒点（圣母、降智、虐主、节奏拖沓）？
3. 爽点是否到位？打脸是否有力？期待感是否拉满？
4. 每章结尾是否有钩子？
5. 字数是否符合预期（3000-5000字/章）？

输出 JSON：
{
  "passed": false,
  "overall_score": 72,
  "issues": [
    {
      "chapter": 1,
      "severity": "critical/warning/suggestion",
      "category": "偏离细纲/毒点/爽点不足/节奏/字数",
      "description": "具体问题",
      "fix_suggestion": "修改建议"
    }
  ],
  "chapter_scores": {
    "1": 75,
    "2": 80,
    ...
  }
}
```

---

### 2.3 重写指定章节 `POST /api/conversation/rewrite-chapter`

**请求：**
```json
{
  "project_id": "神豪经验值",
  "chapter_number": 3,
  "fix_instruction": "第三章主角降智了，应该更果断打脸",
  "model": "deepseek-v4-pro"
}
```

**后端逻辑：**
1. 读取该章细纲 + 前后章正文（保持上下文）
2. 构建重写 prompt
3. 生成后覆盖原文件

### 3.2 状态流转

| 状态 | 显示 | 操作 |
|------|------|------|
| 未生成 | ⬜ 灰色 | — |
| 生成中 | 🔄 蓝色动画 | 可暂停 |
| 已生成未质检 | ⏳ 黄色 | 触发质检 |
| 质检通过 | ✅ 绿色 | 继续下一批 |
| 质检不通过 | ❌ 红色 | 重写/修改 |

## 四、文件输出格式

每章一个 `.md` 文件，格式如下：

```markdown
# 第1章 开局被绿，觉醒系统

正文内容...
（3000-5000字）
```

文件名：`第1章_开局被绿觉醒系统.md`

**兼容现有上传逻辑：**
- 文件名含 `第X章`，可被 `validate_fanqie_project` 识别
- `.md` 格式已被支持扫描和字数统计

## 五、关键技术点

### 5.1 SSE 流式拆分

AI 输出是连续的文本流，需要在前端/后端按 `### 第X章` 标记实时拆分：

- 前端：流式显示全文，同时用正则捕获每章内容
- 后端（可选）：流结束后按标记拆分保存

### 5.2 上下文保持

每卷在一个对话中生成，意味着：
- 第1章生成后，messages 中追加 assistant 的回复
- 第2章继续在同一会话中生成（不需要新开对话）
- 但这样 messages 会越来越长，可能超出上下文限制

**优化方案：**
- 每批次（6章）结束后，总结前6章关键信息，作为新对话的上下文
- 或者每批次新开一个对话，只带设定+细纲+前1章摘要

### 5.3 对齐质检的触发时机

- **自动触发**：每批次生成完成后，自动调用对齐质检 API
- **用户确认**：质检报告显示后，用户点击"通过"才继续下一批
- **强制阻断**：有 critical 问题时，不允许继续下一批

## 六、实现优先级

| 优先级 | 功能 | 说明 |
|--------|------|------|
| P0 | 生成正文 API | 核心功能，SSE 流式输出 |
| P0 | 前端生成页面 | 进度展示、批次控制 |
| P1 | 对齐质检 API | 保证质量的关键 |
| P1 | 自动保存 .md | 按章节拆分保存 |
| P2 | 重写单章 API | 质检不通过时修改 |
| P2 | 状态持久化 | 刷新页面不丢失生成进度 |

---

## 七、成本估算

以 DeepSeek-V4 为例：
- 设定+大纲+细纲（输入）≈ 8000-15000 tokens
- 6 章正文（输出）≈ 18000-30000 tokens
- 对齐质检（输入+输出）≈ 5000-8000 tokens
- **每批次总成本** ≈ 2-4 元
- 一本书 200 章 ≈ 34 批次 ≈ **68-136 元**

比现有串行架构（每章单独调用）大幅降低。
